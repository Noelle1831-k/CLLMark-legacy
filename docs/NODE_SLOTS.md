# 节点粒度水印槽位（node-granular slots）

分支 `claude/node-slots`。本文记录设计、正确性与性能评估、多线程探索和已知局限。所有数据在服务器（32 物理核 / 64 线程）上测得。

## 问题与结论

文件粒度（现有方法）把“一个文件 × 一个规则对”当作一个槽位：嵌入时该规则改写文件里所有匹配节点，整个文件只承载 1 bit。节点粒度把每个可改写的 AST 节点当作一个槽位。

码字是 Hamming(7,4)，每个单元只需要 7 个槽位，所以收益不在“每单元更多比特”，而在**让原来不足 7 个槽位的单元变得可嵌入**。

| 指标（全量 10,810 单元） | 文件粒度 | 节点粒度 |
| --- | ---: | ---: |
| 可嵌入单元 / 容量覆盖 | 5,933 / 54.88% | **6,910 / 63.92%** |
| 消息恢复率 | 99.68% | **100%** |
| 原始码字恢复率 | 93.16% | **99.97%** |
| 原始比特准确率 | 98.99% | **99.996%** |
| TPR / FPR | 99.84% / 2.41% | 100% / 2.20% |
| 功能保持率（配对单元数） | 99.83%（690） | 99.92%（1,453） |
| 1 次规则翻转后恢复（文件粒度=整文件，节点粒度=单节点） | 92.70% | 99.45% |
| 1 次整文件规则归一化后恢复（normalize_1） | 92.70% | **87.51%** |

按语言的可嵌入率（全语料调查）：JavaScript 14.4% → 33.9%，C++ 51.1% → 61.3%，Python 44.5% → 52.8%，C 85.9% → 89.8%。

结论：节点粒度在保持（并提升）嵌入/提取准确率的前提下把容量覆盖提高约 9 个百分点；代价是对“整文件按某规则归一化”的攻击更脆弱，分析阶段 CPU 更高。

## 设计（`cllmark/nodes.py`）

- **站点（site）**：对规则对 (s0, s1)，一个文件的站点是 s0 或 s1 能改写的节点（按先序）。s0 能改写的节点读作 1，s1 能改写的读作 0；C/C++ 的仅检测样式 11/12 以“已是 s0 输出形式”的节点读作 0。改写被拒绝（Reject）的候选不算站点；两种样式都能改写的节点不可读。
- **可用**：用另一比特的样式单独改写该节点会产生空白以外的变化。窗口 = 该改写编辑的文本范围。
- **槽位顺序**：先在“互不相同的节点”上按 (文件, 规则对) 组轮转取下一个可用站点；第一轮即文件粒度的槽位列表（首站点可用时），所以容量足够的单元仍把比特分散到各规则上。不同节点的区域互不重叠、也不相邻。
- **校验**：前 14 个槽位（嵌入用前 7 个，另 7 个备用）必须单独能写入并读回两种比特（排除 `p[i]` → `*(p + i)` 这类改写后逆规则不再识别的单向站点）。槽位仍不足 7 个的单元才允许“叠加”：同一节点承载多个规则对（如比较的操作数顺序与严格性），且该节点所有比特组合都必须能写入并读回。
- **嵌入**：逐规则对、每对一遍改写；每个槽位的节点按字节区间跟随所有编辑（被其他编辑平移，被自身或同节点其他规则的编辑扩展），在标记后代码中按区间（重写过的节点在其自身区域内按目标比特）重新定位。支持文件保存**这些节点在标记后代码中的下标**——从不改为“任意恰好读对比特的站点”，那会让期望消息匹配在不改代码时也成立。读不回的槽位被丢弃并重新放置（最多 8 轮）。
- **提取**：读取存储的前 7 个槽位；缺失或不可读的站点给随机比特（与文件粒度的“不可判定”一致）。
- 支持文件：`{"granularity": "node", "slots": [[file, pair, index], ...], "dropped": n}`。

## 独立模式：不影响文件粒度

节点粒度是独立的模式，默认仍是文件粒度：

- 算法在 `cllmark/nodes.py`（含 `analyze_directory` / `embed_directory` / `extract_directory`），`cllmark/directories.py` 与文件粒度算法不变；CLI 的 `analyze`、`embed` 需显式 `-g node`，`extract` 按支持文件自动识别。
- 基准测试由 `benchmarks/node_engine.py`（`NodeEngine` 继承 `LegacyEngine`）测量，`benchmarks/config-node.json`（只多 `"slot_granularity": "node"`）选择它。度量协议文件 `benchmarks/common.py`、`engine.py`、`utility.py`、`metrics.py` 与文件粒度完全一致，所以普通运行的协议指纹不变、与已有文件粒度结果可比。
- 节点运行时 `research_loop` 把 `node_engine.py` 的摘要写入配置（`node_engine_sha256`），节点模式的协议指纹随其度量代码变化；节点报告在标题下注明粒度。
- 节点模式额外报告 `normalize_k`（整文件逆样式，即文件粒度的 `flip_k`）与 `flip_k`（k 个槽位节点）；`properties` 是站点级：幂等=改写后读另一比特，可逆=再改回得到原文，独立=同文件两槽位交换顺序结果相同。预期消息匹配仍不等同于独立提取。

两种模式共享且已合入的优化（文件粒度结果与改动前逐单元一致）：守卫与改写结果按解析缓存、编辑窗口判断空白变化、`apply_groups`、增量重解析 `edited_tree`、JS 文件事实惰性计算且一次性发布（线程安全）、功能阶段先派发串行项目套件（`runner.functional_priority`）。

## 正确性验证

- 单元测试 `tests/test_node_slots.py`：站点读值、轮转顺序与区域不相交、读回失败的槽位被替换、跨规则对的下标偏移（`a == b` → `not a != b`）、区间跟随、仅检测规则、CLI/目录往返、语料样本上全部 16 种消息往返、增量解析与全量解析一致且不改旧树。
- 全语料调查（全部可嵌入单元 × 16 种消息）：消息匹配 99.994%，原始码字 99.976%，每条消息平均丢弃 0.002 个槽位；仅 5 个单元有失败消息。
- 全量基准（最终代码，源码摘要 `836c26d4`）：文件粒度结果与 main 分支逐单元完全一致；节点粒度多次运行逐单元一致。

## 性能

`tools/perf_benchmark.py --granularity file|node`（292 单元，单核，取 3 次最优）：

| 阶段 | 文件粒度 | 节点粒度 |
| --- | ---: | ---: |
| 分析 | 2.27 s | 5.56 s |
| 规则性质 | 11.20 s | 3.33 s（只在 7 个嵌入槽位上） |
| 提取（4 次） | 1.54 s | 0.85 s |
| 嵌入（含读回校验） | 0.81 s | 0.80 s |
| 合计 | 16.58 s | **11.32 s** |

全语料分析 CPU（16 进程、process_time）：节点粒度为文件粒度的 2.7 倍（函数级 5.4 倍，项目级 1.9 倍），主要花在前 14 个槽位的校验上。

已采用的优化：每次解析内缓存守卫与改写结果；用编辑窗口判断“空白以外变化”而不生成整份文本；同一规则对的所有站点一次改写；增量重解析（`engine.edited_tree`，大文件快 18.5 倍，结果与全量解析一致）；只对前 14 个槽位校验、只对容量不足的单元叠加；更大的站点缓存（内存不计入指标）。

试过并撤回：每个规则对单独编译查询。分析只快约 0.9 s，但在 tree-sitter 0.20.2 下同进程出现偶发（每次全量 1–4 个单元）的语法检查误报，去掉后连续 4 次运行为 0 且结果一致。

## 多线程探索

每一步与最小操作在 1–32 线程下的加速（结果均与单线程比对）：

| 操作 | CPython 3.11（GIL） | 3.14t（无 GIL） |
| --- | ---: | ---: |
| sha256 1 MB（冻结） | 24.4× | 26.8× |
| 子进程启动（测试） | 25.7× | — |
| 64 KB 文件复制 | 1.0× | 4.1× |
| bytes translate / apply_edits | 1.0× | 4.5× |
| json | 0.7× | 10.9× |
| tree-sitter 解析 | 1.0× | 24.8× |
| 查询匹配、守卫、分析、单元流水线 | ≈1.0× | **段错误** |

tree-sitter 0.20.2 与 0.25.2 都未声明支持无 GIL，强制 `PYTHON_GIL=0` 时查询与节点访问在 2 线程即稳定段错误。因此规则分析不能多线程；单元级 64 进程已占满 CPU，单元内并行不增加吞吐（最长单元 2.8 s，无长尾）。

探索中发现并修复：JS 文件事实的惰性计算不是线程安全的（多线程 7–10/10 次结果错误），现改为一次性发布，0/10。main 分支的同一段代码也有此问题（单线程下不触发）。

调度改进：`exclusive` 项目的测试套件共用一把锁串行执行，原先在最后才派发，形成 47.6 s 的串行尾巴。功能阶段改为先派发这些套件（`runner.functional_priority`，不改变结果），空缓存下功能阶段 103.4 s → 74.3 s。

## 已知局限

- 对“整文件按某规则归一化”更脆弱（normalize_1 87.5%，文件粒度 92.7%）：同一规则在一个文件里的多个节点槽位会被同时翻转。
- 新增 1 个功能回归 `js_repo_files/ejs/lib/utils.js`：测试比较 `escapeXML.toString()` 的源码文本，节点改写语义等价但源码变了。任何改写该函数的规则都会触发。
- C 规则 `marked_for` 守卫在无初始化的 `for` 上抛出异常（既有问题）；节点粒度把它当作槽位丢失处理，与文件粒度探针返回 None 一致。
- 分析 CPU 约为文件粒度的 2.7 倍。

## 使用

```bash
.venv-benchmark/bin/python tools/research_loop.py loop --config benchmarks/config-node.json
.venv-benchmark/bin/python -m cllmark embed DIR -l python -b 1010 -o OUT -g node
.venv-benchmark/bin/python tools/perf_benchmark.py --granularity node
```
